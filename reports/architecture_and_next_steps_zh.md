# 当前网络、FloodDiffusion 对照与下一步

2026-09-25，依据本地实际执行代码、官方仓库主配置与论文核对。本文是结构说明和研究路线，不是付费运行申请；没有启动新的 GPU 实验。

**当前网络不是 FloodDiffusion 的去噪主干，也没有加载它的动作生成器权重。** 当前模型是自行实现的关节—时间轴向 Transformer。复用的是 HumanML3D/FloodDiffusion 的富动作特征基础、官方 UMT5 文本编码资产，以及结构化时间场思路。266D 表示、去噪主干、控制输入方式、预测目标和生成循环均有改动。因此，现有失败只能否定当前配置下的控制学习效果，不能否定用户提出的 joint×time 时间场思路。

## 1. 当前模型到底是什么

每帧266D = root4 + 世界XYZ66 + rot6d126 + 局部速度66 + contact4。按关节把原始通道重新排列为22个token，每个最多13个通道，不足处补零；不是把全部动作压成一个13D latent。原始通道都可以无损解包，没有运动编码器或解码器。

输入为当前带噪状态，其中已知位置用真实控制坐标覆盖。对每个关节token，执行：

`h = Linear(动作通道) + Linear(已知通道mask) + Linear(各通道σ)`

`    + MLP(Fourier(有效通道平均σ ×1000)) + 关节embedding + 帧Fourier编码`

这里的 mask 告诉模型“哪些通道是已知的”，σ 告诉模型“每个通道还剩多少噪声”，关节和帧编码提供空间/时间身份。**控制坐标的数值在被覆盖后的动作输入里；mask分支不携带坐标值。没有独立的、每层读取的控制坐标分支。**

随后重复6个复合块：

1. 同一帧，22个关节间的自注意力 + FFN。
2. 同一关节，64帧间的双向自注意力 + FFN。
3. 同文本组再执行对UMT5 token的交叉注意力；无文本组删除它。

这意味着一共12个运动自注意力子层和12个运动FFN，同文本组另有6个文本交叉注意力。宽度256、8头、每个运动FFN宽度1024；普通Pre-LN，dropout=0。使用加法式帧编码，没有在Q/K中使用RoPE，没有Wan式Q/K RMS normalization，也没有逐层的噪声条件shift/scale/gate。

最后 LayerNorm + Linear(256→13)，解包成266D干净动作预测 x0。采样器按当前σ和下一步σ更新活动通道，并把锚点重新固定。下一步输入来自这个真实生成状态；共32步。训练混合解析加噪状态与模型rollout，预测x0，以避免把离开解析轨迹的状态错误地标上原始epsilon−x0速度目标。

本轮是完整64帧窗口的控制实验。去噪迭代中使用上一轮状态，不等于已经实现了不断追加新帧的流式生成。当前结果没有证明实时性。

直接证据：`motion_valley/model263.py:30`、`model.py:12`、`model_no_text.py:9`、`representation266.py:58`、`flow_features.py:47`。

## 2. 与 FloodDiffusion 的差异

| 维度 | FloodDiffusion主配置 | 当前OF003 |
|---|---|---|
| 扩散空间 | 因果VAE编码的4D时间latent，时间约压缩4倍 | 266D显式动作，每帧22个关节token |
| 主干 | Wan-style DiT | 自行实现的轴向Transformer |
| 配置 | 8个block、width1024、8头、FFN2048 | 6个复合block、width256、8头、每个轴FFN1024 |
| 运动交互 | latent时间token的双向注意力 | 关节注意力与时间注意力交替 |
| 时间条件 | 共享时间MLP的输出在每个block用于shift/scale/残差gate | 每次网络调用时，仅在输入显式加入σ相关编码 |
| 位置/注意力细节 | RoPE，Q/K normalization | 加法式帧编码和关节embedding，普通PyTorch注意力 |
| 文本 | 官方UMT5；支持每帧绑定当前文本 | 同文本组复用官方UMT5；本轮每clip固定一条caption |
| 预测 | 主配置预测latent flow velocity | 预测干净动作x0 |
| 时间场 | 时间方向的三角活动窗口 | 关节图距离与时间距离联合定义谷底 |
| 执行 | 滑动窗口与因果解码输出动作流 | 32步生成完整64帧 |

Flood的VAE是因果的，但去噪DiT在可用窗口中是双向的。这两种“因果性”不能混为一谈。本文不把普通PyTorch Transformer块称为原版DiT，也不把共享UMT5等同于共享整套网络。

来源：[论文3.4与附录配置](https://arxiv.org/html/2512.03520v1)、[官方仓库](https://github.com/ShandaAI/FloodDiffusion)。尺寸和模块细节以本地官方 `configs/ldf.yaml`、`models/diffusion_forcing_wan.py:12`、`models/tools/wan_model.py:191` 的实际调用为准。论文描述的文本对齐方式与发布代码的实现细节不完全相同：当前主代码通过逐帧组织context完成对应关系，本文没有声称完全复刻论文所述文本RoPE/偏置mask实现。

## 3. 我准备先做什么

现阶段不能同时改变主干、损失和谷底噪声，再根据一个最终误差猜原因。下一步目标应缩小为：**在一条动作的多个运动学一致状态上，验证控制值能决定自由关节如何变化。**

**第一步：本地审查和最小任务准备。** 沿用已有状态构造，选择一个明确可辨识的控制布局，训练−12/0/+12°，评价−6/+6°。检查控制值确实不同、完整目标一致、无状态标签泄漏；在CPU检查控制到自由输出的计算图连通性。按去噪阶段记录局部变化区域在损失中的贡献，以区分“实现断开”和“信号弱”。已有训练checkpoint只在网络卷，本地静态检查不等于已测过已训练模型的梯度。

**第二步：仅改变控制读取方式的最小对照。** 先保留当前266D、x0目标、同一谷底时间场与骨干，比较当前输入式条件与“每个block额外读取干净控制token”。控制token由目标XYZ、关节位置和帧位置组成；不包含角度ID/动作ID，不引入运动VAE。控制值始终保持干净，生成状态仍逐步rollout。这一步回答独立控制分支是否能改善利用控制值的能力，不能顺便把结果归因于DiT改进。

**第三步：逐层时间调制作为单独结构对照。** 可复用Flood/Wan的共享时间MLP、逐层shift/scale/gate与Q/K normalization思路，适配到joint×time token；必须与前一步分开核算和比较。保留256级别宽度做小样本诊断即可，没有证据要求立即扩到1024。完整替换为更接近Wan的block属于另一项架构变化，不会悄悄混入第二步。

**第四步：控制学会后，再评价谷底的价值。** 在相同已验证骨干、条件路径、训练规模和推理步数下对比uniform与joint×time valley时间场；每个模型训练时使用自身推理的准确时间场，不能只在推理换调度。之后才单独比较干净锚点与加噪锚点。若控制状态加噪，必须保留独立干净目标条件，并承认中间状态不再满足当前“谷底始终σ=0”的合同；这需要用户明确同意，不能从本轮失败自行推导出许可。

每个阶段先看排除固定坐标后的正确响应gain/relative error，以及FK、骨长和速度；重建通过后才恢复多动作、多布局和文本条件。如果局部条件对照仍失败，应先拆查目标、监督权重及优化，而不是直接进入全量训练。实际付费任务的固定配置、步数、门槛和费用会另写完整审批报告；这份路线说明不是运行许可。
